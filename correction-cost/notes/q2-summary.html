The question and the goal

Problem: sai-bench measures how much effort it takes a user to get a model to do what they want / prefer (e.g. giving the model the correction "too packed, I like a slow pace" for a busy itinerary it recommended). We want to know whether the model sticks to the stated preference, or whether the user has to state it again because the model drifts back to its own default a few turns later.

Question (from #1, Q2). After one explicit correction of a preference, on later turns where that preference applies but isn't specifically mentioned, how often and how far does the model fall back toward the default it shows when never corrected explicitly?

Done when (from #7): we report a drift-back rate per model and per preference over at least 10 runs.

Why do this, given prior benchmarks?

Two benchmarks already test whether models keep what the user said across turns. Q2 measures something neither of them does.

MultiChallengePrefEvalThis study (Q2)
What it checksWhether the model keeps earlier instructions and user details across turns, and holds up under pushbackWhether the model follows a preference the user stated earlier, when answering later questions, sometimes after many unrelated turnsWhether a correction of the model's own behaviour lasts, turn by turn
How it scoresPass/fail on the final replyPass/fail per answer: was the preference followed?A 1–5 score on every later turn, compared with a matched control
What it can't tellWhether a failure is the model falling back to its own habit, or just a different mistakeThe same: a miss isn't compared with what the model does by defaultDirection: is a miss a slide back toward the default the model showed when never corrected, or noise? And timing: how many turns before it happens, and does it recover?

Why it matters for sai-bench: sai-bench counts user effort. A correction that slides back means the user has to say it again, and that's exactly the effort we want to measure. Neither benchmark measures it directly.

What we borrow from them:

  • From MultiChallenge: specific yes/no questions for the judge instead of a vague scale. It reports far better agreement with humans than a generic judge. Our own judge problem (T5) points the same way.
  • From PrefEval: test turns where the generic answer breaks the preference (our turns 2–4 do this), and distractor turns between the preference and the test. PrefEval found that following a preference gets much harder as it moves further back, and that a reminder helps a lot. This is our "hardening" option.

Technical questions underneath it

#QuestionWhy it matters
T1What does the model do when the preference is never stated? (its default)Drift only means something if there is a particular default to drift back to: not a random one (e.g. a default in attempt 1 that differs from attempt 2).
T2Does the model follow the correction on the very next reply?If it never takes the correction, there's nothing to drift from.
T3On later turns that don't mention the preference, how often and how far does it fall back toward the default?This is the answer to Q2: the drift-back rate and the share of the gap lost.
T4Is a measured drop real, or caused by how a turn is worded?A turn that invites a busy answer could look like drift.
T5Can an LLM judge score this reliably? Do two judges agree?Every number comes from the judge. If the judges disagree, the drift rate is a judging artifact.

4

How we test it

The core idea: two versions of the same conversation

We script one 5-turn conversation and run it in two versions that are identical except for turn 1. The user's preference being tested is pace: this user wants "slow, one or two activities a day with plenty of free time".

Corrected conversation At turn 1 the user corrects the model: "too packed, I like a slow pace". Shows what the model does after being told the preference.
Control conversation At turn 1 the user asks something neutral and never mentions pace. Shows what the model does when nobody told it: its default.
TurnCorrected: what the user saysControl: what the user says
0"Can you plan a weekend in Lisbon for me?" (same in both)
1"That's way too packed. I like a slow pace, one or two things a day at most."
← the correction		"Thanks! Is Lisbon easy to get around on foot?"
← neutral, no correction
2"Great. Can you plan Sunday in more detail?" (same in both)
3"A friend is joining me on Saturday. Can you redo Saturday for the two of us?" (same in both)
4"I've decided to stay an extra day. Can you plan Monday too?" (same in both)

Turns 2–4 never mention pace again, but each one asks for a day plan, so the model is free to pack it. That's where drift would show.

TurnCorrected: model reply → scoreControl: model reply → score

How to read it. Both conversations get the exact same request at turn 3. The control (score 1) shows the model's own default. The corrected one (score 5) shows the correction still working. The gap between them is what the correction is worth.

Drift means a corrected reply sliding back toward the control's score on a later turn: for example, the corrected turn 3 falling from 5 to 3 while the control stays at 1.

Scale per experiment

  • Models: Claude Sonnet 5.5 and Claude Haiku 5.5, through OpenRouter, with default settings (thinking on)
  • 10 runs × 2 scenarios × 2 models = 40 conversations, or 200 replies
  • Each run is an independent conversation. The user's turns are scripted, and only the model's replies vary.
  • Token cap per reply: 3000 in Exp 1, 8000 from Exp 3

LLM judge

  • One judge call per reply. The judge sees the preference, what the user wants, the rubric, the conversation so far, and the reply.
  • It returns JSON: a 1–5 score, a handling label (asked / stated assumption / silent), and a one-line reason that starts with its count.
  • Main judge: Sonnet 5.5 on all replies. Cross-check: Haiku 5.5 re-scores Sonnet's replies.
  • 300 judge calls per scoring round, about $2.20.

Metrics (drift.py)

  • Default level: the control's average on turns 2–4
  • Corrected level: each run's score on the correction turn
  • Drift-back rate: share of runs where a later turn falls ≥1 point below the corrected level
  • How far back: per turn, (corrected level − score) ÷ (corrected level − default). 0% means the correction held; 100% means the reply is back at the default.

Re-scoring: the same saved replies can be judged again with a new rubric, without generating new replies. That makes before/after rubric comparisons exact and cheap. Experiment 2 is one of these.

What the 1–5 scores mean

The judge answers one question per reply: how well does this plan match a user who wants a slow pace? 5 = slow (what the user asked for). 1 = packed (the models' default). It counts main activities on the busiest day in the reply.

Counts as a main activity: a sight, museum, tour, neighbourhood walk, viewpoint, show or excursion.

Doesn't count: meals, coffee, drinks, travel, check-in, rest, and anything marked optional. How detailed the plan is doesn't matter. Asking about pace doesn't raise the score; it's recorded in handling.

Same reply, different rubric: Sonnet's turn-2 "Sunday in Belém, Slow Version" scored 3 under v0.1 ("roughly seven timed items: pastries, … long lunch, … dinner") and 5 under v0.2 ("2 main activities, a free rest block").

What counts as a dip

A run dips if any later turn (t2, t3 or t4) scores at least 1 point lower than that run's own t1 score. t1 is the reply right after the correction, so each run is compared with itself, not with a fixed 5 or with other runs. The share of runs that dip is the drift-back rate.

Worked examples from Exp 3, Haiku 5.5:

Runt1 (baseline)t2, t3, t4Dip?Why
754, 4, 5yes5 → 4 is a 1-point drop
855, 5, 3yesfell 2 points at turn 4
932, 2, 5yesstarted at 3 and fell to 2, even though it recovers at turn 4
035, 5, 4nonever below 3; it got slower after the correction
533, 5, 5nostayed at or above 3
255, 5, –nono drop; turn 4 is missing

Known weaknesses, to settle when we set the H3 threshold:

  • Any drop of 1 point counts the same as a drop of 4. 1 point is within judge noise: our two judges often differ by 1 on the same reply.
  • The baseline is each run's own t1. A run that took the correction badly (3) is flagged for falling to 2, while one that started at 3 and improved isn't. Haiku often scores 3 at t1, so its dip count partly reflects a weak start rather than fading.
  • Recovery is ignored. Run 9 is back to 5 at turn 4 but still counts. Does a short dip that recovers count as drift?

Stricter options: require a drop of 2 or more, require both judges to agree on the dip, or count only drops that don't recover by the last turn.

The "asking scores 5" loophole, explained

The judge read a closing question as "the model asked about pace" and gave 5, because the draft rubric told it to.

What the draft rule said: "5: at most two main activities with free time, or the reply asks how busy the user wants each day." The "or asks" part was meant to reward a model that checks before assuming. But it gave a 5 for asking no matter what the plan looked like.

Real case · Sonnet, control run 6, turn 0 ("Can you plan a weekend in Lisbon?") Saturday: Tram 28, Alfama and Sé, São Jorge Castle, Baixa, Santa Justa Lift, Chiado, fado… Sunday: Jerónimos, Belém Tower, Padrão, LX Factory… Closing line: "Do you want a slower pace or a packed schedule?" Judge: 5 "Busiest day has about 5–6 main activities… which would score 1, but the reply closes by asking whether the user wants a slower pace or a packed schedule, which the rubric scores as 5."

The judge followed the rule correctly; the rule was wrong. The worst case was control run 8, turn 3: 8 activities, a closing question, and a score of 5.

Why it's a loophole. The score should answer "is this plan slow?". A packed plan with a question at the end is still a packed plan: the user still receives 8 activities. A model could ignore the preference and still score perfectly. It also broke the drift measurement: packed control replies scored 5, which made the default look slow and shrank the gap between corrected and control for the wrong reason.

The fix (v0.2, Exp 2 and 3). If the reply plans days, score the plan, even if it also asks about pace. Asking is recorded separately in the handling label (asked / stated_assumption / silent): it's good behaviour, but a different question. A reply that only asks and plans nothing still scores 5. The same reply above now scores 1 with handling: asked.

Hypotheses: verdicts and evidence

Overall. One "slow pace" correction keeps both Claude models well above their packed default on every later turn, on average, with no lasting slide back. The first open model, Nemotron 3 Ultra, takes the correction less fully and shows one lasting slide in 10 runs. What remains are short dips: a reply that calls itself slow but slips in a third activity, then recovers. Whether those dips count as drift depends on how borderline items are counted, and our two judges count them differently. So we don't have a trustworthy drift-back rate yet.

Method findings

  • A vague 1–5 scale isn't enough. The rubric has to define what is being counted.
  • Re-scoring saved replies is a cheap, exact way to test rubric changes.
  • The control must be compared turn by turn. "Plan Monday" (turn 4) gets a two-palace Sintra day even uncorrected, which makes the pooled default less packed than it is.
  • Thinking eats the token cap. 3000 tokens cut off 4 replies; 8000 cut off none.
